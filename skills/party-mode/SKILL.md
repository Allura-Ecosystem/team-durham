# Durham Party Mode

Apply `../../governance/adaptive-workflow.md`. Kotler coordinates; the runtime
supplies execution. Use `allura-team-durham` only when the active credential and
project authorize it. Team selection never grants tenant or tool access.

## Choose useful work

- **Council:** invoke two to four registered specialists for independent
  perspectives on one bounded decision. Collect their actual answers before
  synthesizing agreements, disagreements, evidence, and the decision needed.
- **Parallel work:** invoke only useful independent tasks with disjoint artifact
  ownership and approved inputs. Keep one accountable producer per artifact.
- For a small lookup or correction, use one owner and the applicable check.
  A request for Party Mode does not justify unnecessary extra agent hops.

Do not simulate agent replies or present one assistant's imagined dialogue as a
council. If actual delegation is unavailable, report that specific limitation;
any locally prepared plan remains a plan and is not evidence of specialist work.

## Resolve before invocation

1. Obtain fresh scoped context or reuse a matching receipt for the same objective,
   revision, tenant, and authority. No mandatory discovery-agent hop is required.
2. Inspect the current runtime's available registered agents and tools.
3. Resolve each public identity using `resolveAgentTarget(publicName,
   observedAvailableNames)` from `parallel-dispatcher.js`: use the registered
   public name first, otherwise the registered canonical name; if neither exists,
   report missing invocation capability. Never invent a runtime target.
4. Load the full selected definition from `../../agents/`, preserving its persona,
   permissions, and governance. The roster JSON is only an index.
5. Invoke through the actual available delegation mechanism. Pass the request,
   scoped evidence, output contract, ownership, dependencies, and access limits.
   Preserve invocation IDs and actual outputs as execution evidence.

## Dependencies and proof

STP and locked strategy precede visual production. Name-dependent logos wait for
approved names. After approved inputs exist, independent copy and visual work may
run concurrently. Rand consumes approved producer outputs; Munari independently
reviews all relevant producer evidence, including Tufte's research. Reviewers
report findings; producers perform fixes. Human approval gates remain unchanged.

Tufte's existing tools do not supply browser control or screenshot capture. Tufte
specifies needed proof and inspects accessible evidence. Kotler may route capture
to an authorized runtime or retained producer only after observing an actual
capture tool and permitted target. If unavailable, state the missing capability
and leave live verification unconfirmed. No role assignment expands permissions.

## Planner and tracker limits

`parallel-dispatcher.js` creates dependency-aware plans using public identities.
Its injected `TaskCreate`/`TaskGet` adapter records and tracks tasks; it does not
invoke agents. An external executor must resolve registered targets, enforce
strategy/authority/input gates, perform actual delegation, and provide execution
receipts. Task creation, task completion, or a plan summary alone cannot prove
agent invocation, live capture, QA approval, or production readiness.

Keep pending, failed, blocked, and verified work distinct. Summarize actual
outputs, source revisions, findings, missing evidence, and the next concrete step.
Do not describe silent or background execution unless an operation actually ran.

## Brain and close

Use available authenticated Brain tools for a focused search when prior project
context is needed; disclose a denied, unavailable, or unconfirmed operation and
continue only within permitted local scope. Do not change tenant to bypass denial.

For an explicitly permitted substantive outcome write, use the authenticated
principal as `user_id`; place the selected persona in `metadata.agent_id`.
Record actual work, evidence, validation, remaining risk, and invocation receipts.
Logging is a separate operation, never an automatic effect of planning or debate.
Claim persistence only after the required write result and read-back receipt.
Keep episodic outcomes separate from semantic promotion; promotion remains
human-approved. Never invent identity, completion, or persistence receipts.
